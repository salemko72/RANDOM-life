# LISTEN playlist integration

LISTEN / SLUŠAJ remains the sixth UI category; GO stays. The selector uses fifteen existing Spotify playlist references (name, ID, mood), three each for energy, ambient/chill, feel-good classics, upbeat, and mellow/wistful. No playlist tracks, audio, artwork catalog, or additional metadata are imported into D1/R2. The four old demo track references are retained only so existing saved/history entries still open.

Every fresh LISTEN spin chooses an ambient/chill playlist. Choosing a mood selects one of that group's three playlists and requests playback immediately, avoiding the immediately previous playlist. Selection handles random boundaries and defaults unknown moods to calm. Playlist order and subsequent songs are controlled by Spotify; we do not import tracks or promise access to Spotify's recommendation algorithm.

A connected Premium account starts the complete playlist using `PUT /v1/me/player/play` with `context_uri: spotify:playlist:<id>` and the existing SDK device. Old saved tracks still use `uris`. The app does not fetch playlist contents, request more scopes, or repeatedly start each subsequent song. Current title, artist and artwork are read from SDK playback-state events. The heading identifies the selected playlist; the player identifies the actual current track.

The iframe fallback uses the playlist URI, including the manual playlist embed when the IFrame API fails. Provider/account/browser restrictions still apply. A single persistent player continues across other category spins; the small upper-right control opens the song view, pauses/resumes or stops playback. A new LISTEN spin stops the previous music and selects another calm playlist. The existing silent Premium preparation and gesture activation remain intact. No playback with the phone locked/app closed is promised.

Playlist favorites/history use `listen:playlist:<id>`. Legacy `listen:<track-id>` keys remain valid. Sharing sends the direct Spotify playlist URL; strict share parsing accepts only exact HTTPS track/playlist URLs, with no query/hash/alternate origins. Opening content does not mark it listened. Native subframe navigation accepts only exact track/playlist Spotify embed paths; no APK/AAB is built in this task.

## Verification and rollout

`node --use-env-proxy scripts/verify-listen-playlists.mjs` checks each reference against public Spotify oEmbed metadata and writes an evidence report to `/tmp/lifespinner-playlist-verification.json`. It exits nonzero on inaccessible metadata, title mismatches or missing titles. This is metadata validation, not proof of authenticated playback, regional availability or current integration policy compliance.

At implementation time, Spotify destinations were denied by the cloud environment's restricted network policy. The fifteen references are candidates until this script and official-documentation review can run successfully; do not present them as verified or deploy this catalog before that review. Changes to the environment settings failed to publish in the user's UI; the active policy remained restricted at revision 57. This does not imply a problem with the app or the user's Spotify account.

`tests/listen.test.ts` checks grouping, selection, saved compatibility and strict share destinations. `tests/spotify-auth.test.ts` checks context versus track requests and authorization failure handling. Browser smoke scripts simulate Premium/iframe providers, all mood changes, next-song metadata, no duplicate starts, persistent background playback, narrow-screen controls, pause/stop, offline/manual fallback and account isolation. Actual Spotify login/playback still require physical browser/account testing. Backend contracts, Studio, content, existing download artifacts and native package versions remain unchanged.
